# Following a factory change request to merge

The orchestrator follows every change request it opens, `approved` and `needs-review` alike, until it is merged or closed. It does this itself rather than through an ad-hoc helper, because it is the only writer of item status and the only one that can send review fixes back through the factory.

## Contents

- Watching
- Approval to merge
- Review findings and failed checks
- Reconcile records

## Watching

1. Read the change request's state with the installed `10kr-change-requests` skill's status read: required checks, people's reviews, and unresolved threads. Where `forge-github:10kr-babysit-pr` is installed, its loop may do the watching, but only the watching: never let it edit, fix or merge.
2. While a session runs the loop, wait with the harness's waiting tools, such as a background check watch or Monitor, rather than polling in a busy loop.
3. This project has no review bot and requires no approvals (`factory/policy.md`), so the factory's own review and approve stations are the review: there is no bot to re-trigger.
4. In `dark`, schedule auto-merge only for an `approved` item, after refreshing its base (merge current `origin/main` with a merge commit, `nix develop .#ci --command just ci`, `nix develop .#ci --command git push origin <branch>`), and bound to the new head with `gh pr merge <n> --auto --squash --match-head-commit <new head>`, so a head that moved afterwards fails to schedule. The only commits between the approved head and the new head are clean merges of main. A `needs-review` change request is never scheduled on the factory's own say-so; it waits for the maintainer's approval (below). The merge guard hook (`.claude/hooks/factory-merge-guard.sh`) refuses to merge or schedule any pull request that touches a `factory` path, except on the maintainer's recorded instruction for that pull request and head: the merge carries `--match-head-commit <sha>` for the current head, and a person under `## Roles` in `factory/policy.md` (read from `main`, never the branch) approved a commit on the branch with only clean merges of `main` after it, or applied the `factory:approved` label after the branch's last own commit. The hook verifies this itself through `gh api` and `git merge-tree`, with a timeout on every read, and denies when it cannot read any of it in time; it is not a blanket bypass, and it never covers scheduling auto-merge (`--auto`) of a `factory` pull request, since a scheduled auto-merge stays enabled across later pushes; the approval merge sequence merges at once, pinned, after the checks pass. Never add the `factory:approved` label yourself and never submit an approving review (`gh pr review --approve`, a `pulls/<n>/reviews` write with `event=APPROVE`, or the GraphQL review mutations), all of which the hook blocks, because a review from the account agents act as would count as a Roles approval; never work around the hook, and never use its `FACTORY_MERGE_APPROVED` override, which is for a person's explicit instruction in the session only.

## Approval to merge

Factory change requests are authored by the maintainer's own account, today the only `## Roles` account, and GitHub does not let an author approve their own pull request, so the `factory:approved` label is the maintainer's practical approval; a review counts only from another Roles account that did not author it. A `needs-review` change request is approved when a person under `## Roles` in `factory/policy.md` (as `main` has it) left an `APPROVED` review, still their latest decisive review, on a commit with only clean merges of main after it, or applied the `factory:approved` label after the branch's newest own commit. A clean merge of main has a tree exactly equal to `git merge-tree --write-tree` of its parents; a hand-resolved conflict or an extra edit makes it an own commit, which voids the approval. Reconcile then merges it by the approval merge sequence in `SKILL.md`: merge current `origin/main` into the branch (no force push; skipped when the branch already contains it), run `nix develop .#ci --command just ci`, push with `nix develop .#ci --command git push origin <branch>`, wait until required checks are reported on that head and then for `timeout 45m gh pr checks <n> --required --watch --fail-fast`, and run `gh pr merge <n> --squash --match-head-commit <that head>`. A wait that times out changes nothing; the next reconcile tries again. A required check that failed for a transient or infrastructure reason is rerun first (step 5 below), so it never costs the approval. A conflict (`git merge --abort`), a red gate (`git reset --hard origin/<branch>`, since the merge was never pushed) or a required check the change failed (the clean merge is already pushed; nothing to undo) removes `factory:approved`, comments on the change request and requeues the item at build with the failure as a finding and the change request as `change`. When the merge command itself fails, nothing is undone: a moved head is re-checked on the next reconcile, a guard denial (such as a review GitHub dismissed on the refresh push) gets a comment asking for the `factory:approved` label, and a ruleset block goes to `awaiting-human`. Before any merge or schedule, `git diff --name-only origin/main...<branch>` must show no `.claude/agent-memory/` path; one that does is requeued with that finding instead.

## Review findings and failed checks

Review fixes always go through the factory, never as hand edits, because a hand edit skips the build gates, the review lenses and the approver. When a factory change request gets a request for changes, unresolved threads from the bot or a person, or a required check that fails because of the change:

1. Verify each finding with `engineering-core:review-verifier`, through `engineering-core:10kr-receiving-code-review`.
2. Answer each finding that does not hold up in its own thread, with the evidence.
3. For the findings that hold up, post the item's resume state (`references/queueing.md`) with them as `findings` and the change request's link as `change`, and requeue the item at station `build`, `queued`, unassigned. Leave the change request open.
4. When its slot comes up, fetch `factory/<item>` and launch the rework run on that branch. The builder merges current `origin/main` into it first, then adds commits on top; never rewrite history, because the change request is open and reviewers' approvals point at its commits. The run goes through review and approve again. On `approved` or `needs-review`, push the branch with `nix develop .#ci --command git push origin factory/<item>`, never with force, instead of opening a new change request, then reply to and resolve each addressed thread, request review again, and keep following the change request.

   Remove the `factory:approved` label (`gh pr edit <n> --remove-label factory:approved`) *before* any push other than a clean merge of main: a rework push, the push in a requeue (`references/queueing.md`, "Requeue" step 2), and the push before posting a resume state. The committer date of the branch's newest own commit says nothing about when the commit was pushed, so a commit made before the label but pushed after it (a rework committed before the maintainer labels the old head, or a label re-applied between this removal and the push) would inherit the approval by date alone. The merge guard and Reconcile therefore also check the branch's push times, and accept the label only when the head at the moment it was applied was the newest own commit or a clean merge of main after it. Removing the label first means it never sits beside commits nobody reviewed; a person adds it again after reviewing the new head.
5. A check that failed for a transient or infrastructure reason is rerun or reported as `engineering-core:10kr-ci-failure-follow-up` directs, not requeued, because the change did not cause it.
6. The no-progress check in `references/queueing.md` applies: findings that recur with nothing addressed, or a `needs_human` flag, send the item to `awaiting-human` with an options brief.
7. The approver's classification of the new head decides whether auto-merge is allowed, exactly as on the first run.

## Reconcile records

Append one follow-up line to `factory/metrics.jsonl` per forge event, never twice: `{item, event: "reviewed"|"merged"|"closed"|"reverted", ref, reviews: [{role, verdict}], outcome, at}`, where `ref` identifies the event (the review's id, or the merge or close time). Before appending, skip any `ref` already recorded for that item. Reverts come after an item is closed, so check them separately: for every item with a `merged` line and no `reverted` line in `factory/metrics.jsonl`, look on the default branch for a later commit that reverts its merge commit (git's own revert, which names the reverted commit), and record `reverted` when one exists.
